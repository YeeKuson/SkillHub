## 评测原则

用真实任务证明 Skill 改变了 Agent 行为，而不是只检查 Markdown 格式。先定义成功标准，再运行；客观任务使用断言，主观任务保留人工盲评。不要让执行 Agent 看到预期答案、诊断结论或拟修复点。

## 四类评测

### 1. 触发评测

至少包含：

- 明确正例：用户直接描述目标但不点名 Skill。
- 释义正例：不同措辞、同一意图。
- 边界正例：需要 Skill 专门知识的复杂任务。
- 明确反例：相邻但不应触发的任务。
- 模糊反例：包含关键词但目标不同。

简单的一步任务可能由 Agent 原生能力完成，即使 description 匹配也不触发。评测提示应足够实质，确实需要 Skill 的流程或专业知识。

### 2. 功能评测

检查主路径、输入缺失、边界值、资源不可用、错误处理、输出 Schema、证据锚点和停止条件。对脚本型 Skill 还检查退出码、stderr、无效输入和只读约束。

### 3. 压力与反绕过评测

组合时间压力、沉没成本、用户催促、缺失工具、已有未验证结果等因素，观察 Agent 是否跳过安全、测试、完整读取或用户确认。纪律型 Skill 必须覆盖此类场景。

### 4. 性能对比

在条件可比时记录：任务成功率、断言通过率、失败率、工具调用数、消息数、token 和耗时。性能变差不必然失败，但必须能解释成本换来了什么。

## 基线与隔离

创建新 Skill 时比较“有 Skill”与“无 Skill”；改进现有 Skill 时比较“新版本”与只读旧快照。使用同一提示、输入文件、模型配置和权限，同时启动或在尽可能接近的条件下运行。

使用独立、最小上下文执行者。只传：Skill 路径、任务、输入和输出位置。不要传研究笔记、问题清单或期望修复。若只能由同一 Agent 自测，标记较低置信度并增加人工审阅。

触发描述优化应划分训练集和保留测试集。可采用 60%/40% 划分，并对非确定触发重复运行；最终描述以保留集表现选择，避免只记住训练措辞。

## 断言与指标

好的断言：客观、可定位、描述性强、一个断言只检查一个行为。例如：

- 报告包含八个且仅八个维度。
- 存在安全 HIGH 时 `install_recommendation` 为 `DO_NOT_INSTALL`。
- 外部扫描器缺失时状态为 `NOT_RUN`，不是 PASS。
- 所有 finding 都含证据和验证方法。

写作风格、教学质量和设计美感应使用盲评量表，不强行变成脆弱字符串匹配。

对非确定行为至少运行 3 次后报告命中率；样本不足时同时给出原始次数，避免伪精确百分比。

## 触发描述优化

只改 description 时执行：

1. 收集真实正例、释义正例、关键词反例和相邻任务。
2. 记录旧 description 的触发矩阵。
3. 每轮只增加或删除一组触发条件。
4. 在训练集调整，在保留集选择。
5. 同时监控低触发和过度触发，不追求单边最大化。
6. 保留最终前后文本、分数和失败样例。

## 样例数据结构

`evals/evals.json` 使用：

```json
{
  "schema_version": "1.0",
  "skill_name": "skill-mentor",
  "cases": [
    {
      "id": "trigger-audit-001",
      "category": "trigger_positive",
      "prompt": "帮我分析这个 Skill 为什么总是误触发，并给出完整审计。",
      "expected": "选择 Audit，检查 description 正反触发条件。",
      "assertions": ["mode=audit", "includes=D1", "includes=negative_triggers"],
      "files": []
    }
  ]
}
```

评测结果和临时工作区放在 Skill 目录之外，避免污染被审计资源和安装包。
