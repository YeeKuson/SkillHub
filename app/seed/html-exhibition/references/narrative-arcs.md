# 演示叙事引擎（narrative arcs）

这是本 skill 的原创内核。它的工作只有一件：**把"理解层"产出的要点，重组成一场给观众的演示叙事，输出逐页大纲。**

## 先记住三句话

1. **demo 不是说明书，也不是教程。** 说明书给开发者查，教程循序渐进教学，demo 是给观众的**一次性叙事**——观众只看一遍，听你讲一遍，记住一句话就够本。
2. **演示是减法。** 理解层可能有 20 个点，一场演示只留能推进叙事的 5–7 个。砍掉的不是"次要内容"，是"会稀释主线的内容"。
3. **每一页只承担一个目的。** 一页讲不清两件事；讲两件就拆两页。

## 通用弧线（所有类型的底座）

```
钩子 → 问题 → 洞察 → 方案 → 证据 → 收束（记住的一句话 / 下一步）
```

- **钩子**：第一页 3 秒内让人想往下看。一个反常识、一个尖锐的问题、一个真实场景，别用"大纲页 / 自我介绍页"开场。
- **问题**：观众为什么该关心？把痛点讲具体，最好能让观众"对，我也烦这个"。
- **洞察**：你看到了别人没看到的什么？这是整场演示的"为什么是你/为什么是这个方案"。
- **方案**：你做了什么。只讲和洞察直接相关的核心，不堆功能清单。
- **证据**：凭什么信？数据、对比、现场 demo 效果、git 历史、用户反馈。**没有证据的方案是 PPT 味的空话。**
- **收束**：把观众该记住的一句话钉进去，给明确的下一步（试用 / 反馈 / 决策 / 投入）。

---

## 三条具体弧线（按演示对象选一条）

### 弧线 A：项目类（已有代码 / 已做出来的东西）

适用：给你自己或团队展示一个做完/在做的项目。

```
1. 钩子      一句话说清这个项目让什么变得不一样了
2. 旧世界    没有它之前，事情有多麻烦（具体场景，不抽象）
3. 转折      你发现的关键洞察 / 技术巧思（这是全场记忆点）
4. 怎么做的  核心机制，配 1–2 段关键代码或一张架构图
5. 看效果    现场 demo / 前后对比 / 关键数据（证据，最重磅的一页）
6. 边界      诚实说它不做什么、当前限制（反而更可信）
7. 下一步    路线 / 你需要什么（反馈、资源、采纳）
```

理解层喂入：用 Cogent 的"技术巧思"和"代码说明书"填第 3、4 页。

### 弧线 B：想法类（还没做 / 可能性预测）

适用：你提到的"用 html 替代 PPT 做可能性成果预测"的场景。最难，因为信息稀薄。

```
1. 钩子      一个让人愣一下的假设 / 数字 / 趋势
2. 痛点      现状哪里不对，谁在为此付代价
3. 假设      "如果……会怎样" —— 你的核心赌注
4. 凭什么    支撑这个假设的信号（趋势、案例、第一性推理）
5. 长这样    用具象画面/原型描述"它做出来是什么样"，让人能想象
6. 风险      最大的不确定性是什么（主动暴露，比藏着可信）
7. 第一步    最小可验证动作，把"大想法"落到"下周能做的事"
```

⚠️ 想法类信息天然不足，**叙事容易空**。理解层若信息稀薄，必须先用引导式提问向用户补：核心赌注是什么、有什么信号支撑、最大风险在哪。补不齐就别硬做成一场假大空演示。

### 弧线 C：成果/复盘类（已经发生的结果）

适用：工作汇报、阶段复盘、项目结案。

```
1. 钩子      最重要的那个结果数字 / 结论，开门见山
2. 目标      当初要解决什么、成功标准是什么
3. 做了什么  关键动作（只留改变了结果的，不流水账）
4. 结果      数据说话，前后对比，达成 vs 预期
5. 为什么    结果背后的真实原因（成了为什么成、没成为什么没成）
6. 学到什么  可迁移的判断，不是套话总结
7. 下一步    基于复盘的具体决策
```

---

## 从要点到大纲的操作步骤

1. 判断演示对象属于 A/B/C 哪一类。
2. 选对应弧线，把理解层的要点**分配**到弧线的各个阶段。
3. 做减法：每个阶段 1–2 页，全场控制在 7–12 页。删掉放不进弧线的点。
4. 为每一段写四行：
   - **目的**：这段要让观众产生什么反应？
   - **核心信息**：一句话（这句话就是主标题的来源）。
   - **版式建议**：去 `layout-archetypes.md` 选一个原型 ID。
   - **概念动画**：这段有没有"真实行为 / 机制"值得演？有就写"用什么视觉隐喻演哪个事实"（如：飞机临门才爬=晚指令）；纯陈述 / 纯数据段写"无，用通用动效"。详见 `motion-grammar.md` 概念动画节。
5. 把大纲**和概念动画设想一起交给用户对齐**——这就是 SKILL.md ①里的强制确认门。**对齐前不生成 HTML。** 信息薄、是宽泛指令时，宁可多问一轮再画。

## 大纲产出模板

```
演示对象：<一句话>
弧线类型：A / B / C
记住的一句话：<整场演示的收束>

P1  [目的] ... [核心信息] ... [版式] cover           [概念动画] 无
P2  [目的] ... [核心信息] ... [版式] problem-scene   [概念动画] 用 X 演出"Y 这个真实问题"
P3  [目的] ... [核心信息] ... [版式] insight-statement [概念动画] 无，用通用动效
...
```

## 反面清单（叙事层禁止）

- ❌ 用"目录页 / 议程页 / 自我介绍页"开场——浪费最宝贵的第一页。
- ❌ 功能罗列代替叙事（"我们有 A、B、C、D…"）。
- ❌ 没有证据页就下结论。
- ❌ 一页塞两个核心信息。
- ❌ 结尾放"谢谢观看 / 总结一下"的空话页，而不给记忆点和下一步。
- ❌ 把 Cogent 的代码说明书原样搬上页面——那是给开发者查的，不是演示。
- ❌ 讲文件索引而非功能（堆 commit hash / 文件名 / tag / HEAD 号）——观众听的是"它干什么"，不是"代码在哪"。
- ❌ 一段堆多条注脚 / 写本地化、reduced-motion 这类开发者免责声明——演示正文要干净，元信息删掉。
